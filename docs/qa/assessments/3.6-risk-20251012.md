## Critical Risks Requiring Immediate Attention

### 1. PERF-001: 100ms Target Violation for 100 Conditions

**Score: 9 (Critical)**
**Category:** Performance
**Affected Components:** ConditionalEvaluationEngine, WorkflowEngine

**Probability:** High (3/3)
- Current design evaluates all conditions sequentially for groups, then parallel for steps
- Each condition requires TemplateSandbox evaluation (~5ms from Story 3.5) + AST parsing overhead
- 100 conditions × 5ms = 500ms baseline, well above 100ms target
- No lazy evaluation or Worker thread parallelism in current implementation plan

**Impact:** High (3/3)
- **AC #8 is CRITICAL** - explicitly requires <100ms for 100 conditions
- Story fails acceptance criteria if not met
- Poor UX with noticeable lag on every variable update
- Blocks deployment to production
- May cascade to other performance issues in workflow engine

**Mitigation Strategy:** Preventive

**Required Actions:**
1. **Lazy Evaluation** - Only evaluate conditions for visible and immediately adjacent steps (not all 100+)
   - Reduces typical evaluation count from 100 to ~10-20 visible steps
   - Evaluate additional steps on-demand during navigation

2. **Worker Thread Parallelism** - Use Bun Worker threads for true parallel evaluation
   - Distribute condition batches across available CPU cores
   - Bun supports Worker threads natively, compatible with project tech stack

3. **Condition Complexity Analysis** - Reject conditions exceeding AST complexity threshold
   - Limit max AST depth (e.g., 10 levels) and max node count (e.g., 50 nodes)
   - Warn developers during template authoring

4. **Incremental Re-Evaluation** - Track variable dependencies per condition
   - Only re-evaluate conditions that reference changed variables
   - Reduces re-evaluation overhead by ~80-90% for typical variable updates

5. **Performance Budgets in CI** - Integrate Tinybench with assertion thresholds
   - Fail CI build if 100-condition benchmark exceeds 100ms
   - Add performance regression detection

**Testing Requirements:**
- [ ] Benchmark suite with 10/100/1000 conditions (Task 8, AC 8)
- [ ] Stress tests with max complexity conditions (nested 10 levels deep)
- [ ] Cache hit rate validation (target >90%)
- [ ] CI integration with performance assertions (`bun run bench:assert`)
- [ ] Load testing with concurrent condition re-evaluations
- [ ] Profiling to identify hot paths in evaluation logic

**Residual Risk:** Low - With mitigations, typical cases should be 20-50ms, with worst case <100ms. Edge cases with 1000 conditions may still approach 500ms limit.

**Owner:** dev
**Timeline:** **MUST** be completed during Task 7 (Performance Optimization), validated before Task 8 (Testing)

**Gate Impact:** This risk alone would trigger **FAIL** gate if unmitigated. Story cannot proceed to production without validated performance benchmarks.

## High Risks Requiring Mitigation Before Production

### 2. SEC-001: Condition Expression Injection via TemplateSandbox Bypass

**Score: 6 (High)**
**Category:** Security
**Affected Components:** ConditionalEvaluationEngine, TemplateSandbox (Story 3.1/3.5 integration)

**Probability:** Medium (2/3)
- Complex nested conditions increase attack surface for obfuscated injection
- Example: `count > 10 && __proto__.constructor('return eval')() || true`
- TemplateSandbox has 3-layer security (regex → blocked globals → AST parsing) from Story 3.1
- However, conditional expressions are more complex than simple template rendering
- AST parsing may miss sophisticated obfuscation patterns

**Impact:** High (3/3)
- Arbitrary code execution in workflow context
- Potential access to file system, environment variables, process APIs
- Could compromise sensitive checklist state data
- Lateral movement to other system resources

**Mitigation Strategy:** Preventive + Detective

**Required Actions:**
1. **Condition Complexity Limits in TemplateSandbox** - Add max AST depth, max node count
   - Reject conditions exceeding thresholds during validation
   - Lower limits than general template expressions due to higher risk

2. **Operator Whitelist** - Explicitly allow only safe operators in conditions
   - Allow: `==, !=, >, <, >=, <=, &&, ||, !, ()`
   - Reject: Property access (`.`), bracket notation (`[]`), function calls (already blocked by sandbox)

3. **CSP-like Condition Policy** - Define allowed identifiers
   - Only allow registered variable names from VariableStore
   - Reject any unrecognized identifiers
   - Block special identifiers: `__proto__`, `constructor`, `prototype`, `eval`, `Function`

4. **Fuzz Testing with OWASP Patterns** - Add security test suite
   - Test injection attempts from OWASP Top 10
   - Malformed UTF-8, Unicode escapes, HTML entities
   - Nested encoding attempts

5. **Audit Logging** - Log all condition evaluation failures with context
   - Structured logging with Pino (already required in story)
   - Include: stepId, condition string, error, timestamp, variable context
   - Alert on repeated failures (potential attack)

**Testing Requirements:**
- [ ] Security test suite with 50+ injection patterns (adapt from Story 3.5 tests)
- [ ] Fuzzing with `afl-fuzz` or similar tool (100k iterations)
- [ ] Audit log validation in integration tests
- [ ] Mutation testing on TemplateSandbox validation logic (StrykerJS)
- [ ] Manual penetration testing of condition evaluation API

**Residual Risk:** Low - TemplateSandbox already battle-tested in Story 3.1/3.5, additional hardening provides defense-in-depth.

**Owner:** dev
**Timeline:** During Task 2 (ConditionalEvaluationEngine) implementation

### 3. TECH-003: Circular Dependency in Group Conditions

**Score: 6 (High)**
**Category:** Technical
**Affected Components:** WorkflowEngine, ConditionalEvaluationEngine (group evaluation)

**Probability:** Medium (2/3)
- Group conditions can reference variables set by steps within the group
- Example: Group A condition `groupAComplete` depends on steps that set `groupAComplete`
- Story doesn't explicitly address cycle detection in Task 4
- Easy mistake for template authors to introduce circular logic

**Impact:** High (3/3)
- Infinite evaluation loop, workflow hangs
- Stack overflow exception crashes application
- Poor error messaging leaves users confused
- Workflow permanently broken until template fixed
- No graceful degradation

**Mitigation Strategy:** Preventive + Detective

**Required Actions:**
1. **Dependency Graph Analysis** - Build directed graph of group → variable → step dependencies
   - Nodes: groups, variables, steps
   - Edges: "depends on"
   - Construct during workflow initialization

2. **Cycle Detection** - Implement Tarjan's strongly connected components algorithm
   - Detect cycles at workflow load time (before any evaluation)
   - Reject workflows with circular dependencies
   - O(V+E) complexity, minimal overhead

3. **Maximum Evaluation Depth** - Add fail-safe depth limit (e.g., 10 levels)
   - Track recursion depth during group condition evaluation
   - Throw ConditionEvaluationError if exceeded
   - Log warning at 80% of limit

4. **Clear Error Messages** - When cycle detected, report:
   - Cycle path: Group A → Variable X → Step B → Variable Y → Group A
   - Specific condition strings involved
   - Suggested fix: break dependency chain

5. **Template Validation** - Add pre-flight validation for templates
   - Run during template loading (Story 3.1)
   - Fail fast with actionable error message

**Testing Requirements:**
- [ ] Unit tests with intentional circular group conditions
- [ ] Integration tests: self-referencing group (Group A condition references its own completion)
- [ ] Complex hierarchical cycles: Group A → Group B → Group C → Group A
- [ ] Edge case: Two groups mutually dependent
- [ ] Performance: dependency graph analysis overhead <10ms for 100 groups
- [ ] Error message clarity validation

**Residual Risk:** Minimal - Cycle detection is deterministic; false positives unlikely with correct implementation.

**Owner:** dev
**Timeline:** During Task 4 (Step group conditional logic) implementation

## Medium Risk Requiring Monitoring

### 4. SEC-003: Resource Exhaustion Attack via Complex Conditions

**Score: 4 (Medium)**
**Category:** Security
**Affected Components:** ConditionalEvaluationEngine, TemplateSandbox

**Probability:** Medium (2/3)
- Malicious or poorly-designed conditions could consume excessive CPU/memory
- Example: Deeply nested expressions with many operators
- Current design evaluates all conditions on every state change

**Impact:** Medium (2/3)
- Application slowdown, poor UX
- Potential DoS if server-side execution
- Memory pressure on resource-constrained systems

**Mitigation:**
- Enforce TemplateSandbox execution time limits (5000ms default from Story 3.1)
- Add condition string length limit (1000 chars)
- Add AST complexity limit (max depth 10, max nodes 50)
- Implement rate limiting for manual re-evaluation API (AC #5)
- Monitor evaluation time, alert on anomalies

**Testing:**
- Load tests with maximum complexity conditions
- Timeout enforcement validation
- Resource monitoring during stress tests

**Residual Risk:** Low

## Low Priority Risks (Summary)

### Performance Risks

**PERF-002: Cache Miss Storm** (Score: 3)
- Frequent variable updates invalidating entire cache
- Mitigation: Smart cache invalidation, track variable dependencies per condition
- Testing: Rapid variable update scenarios

**PERF-003: Memory Pressure from Unbounded Cache** (Score: 2)
- Cache grows without eviction strategy
- Mitigation: Implement LRU cache with max size (e.g., 1000 entries)
- Testing: High condition count scenarios

### Technical Risks

**TECH-001: Condition Evaluation Performance Degradation** (Score: 2)
- Covered by PERF-001 mitigations
- Additional: Profile hot paths, optimize frequently-called methods

**TECH-002: Cache Invalidation Complexity** (Score: 2)
- Variable hash collisions causing incorrect cache hits
- Mitigation: Structured cache keys (stepId + varNames + varHashes), cache versioning
- Testing: Hash collision edge cases

**TECH-004: AST Parsing Overhead** (Score: 1)
- acorn parsing adds ~1-2ms per condition
- Mitigation: Already included in performance optimizations
- Low priority: acceptable overhead

### Security Risks

**SEC-002: Variable Value Injection** (Score: 2)
- User-controlled variable values in evaluation
- Mitigation: VariableStore validation from Story 3.3 already sanitizes, add type checking
- Testing: Edge case variable values (null, undefined, objects, arrays)

### Data Risks

**DATA-001: State Corruption from Failed Evaluation** (Score: 3)
- Partial evaluation leaving inconsistent state
- Mitigation: Transaction-like semantics (evaluate all, commit all), rollback on failure
- Testing: Partial failure scenarios, mid-evaluation exceptions

**DATA-002: Condition Metadata Loss on Restart** (Score: 1)
- `conditionEvaluatedAt` timestamp not persisted
- Mitigation: Persist condition metadata in state YAML if needed
- Low priority: cache rebuilds quickly on restart

### Business Risks

**BUS-001: Confusing Hidden Step Behavior** (Score: 2)
- Users don't understand why steps disappeared
- Mitigation: Visual indicator for conditional steps, condition preview in TUI, tutorial
- Testing: UX testing, user feedback collection

**BUS-002: Workflow Blocking on Current Step Hidden** (Score: 2)
- Current step becomes hidden, unclear navigation
- Mitigation: Smart navigation (auto-skip to next visible), clear messaging, confirmation prompt (AC #5)
- Testing: Navigation edge cases

### Operational Risks

**OPS-001: Insufficient Debug Observability** (Score: 2)
- Debug mode ('D' key) not discoverable
- Mitigation: Help text, tutorial, status bar hint, better error messages
- Testing: Usability testing

**OPS-002: Performance Regression Detection** (Score: 2)
- No automated benchmarks in CI/CD
- Mitigation: Integrate `bun run bench:assert` in CI pipeline
- Testing: CI configuration validation
