## Critical Risks Requiring Immediate Attention

### 1. TECH-001: Git Repository Integration Complexity

**Score: 9 (Critical)**
**Category**: Technical
**Probability**: High (3) - Git operations are environment-dependent and inherently error-prone across different systems, authentication methods, and network conditions
**Impact**: High (3) - Core marketplace functionality (template discovery, download, versioning) depends entirely on reliable Git operations

**Affected Components**:
- `GitTemplateRepository` (packages/core/src/templates/repositories/GitTemplateRepository.ts)
- `TemplateVersionManager` (packages/core/src/templates/TemplateVersionManager.ts)

**Detailed Risk Analysis**:

The story implements Git operations using `Bun.spawn(['git', ...])` for cloning, fetching, and listing versions. This introduces multiple failure points:

1. **Environment Variability**: Git behavior varies across OS (macOS, Linux, Windows), Git versions, and system configurations
2. **Network Failures**: Timeouts, DNS failures, proxy issues, firewall restrictions
3. **Authentication Complexity**: SSH keys, HTTPS tokens, credential storage, permission issues
4. **Process Management**: Spawn failures, hanging processes, zombie processes, stderr parsing

**Example Failure Scenarios**:
- User has outdated Git version lacking `--depth` flag
- SSH agent not running, causing authentication hang
- Large repository clone exceeds default timeout
- Network interruption during fetch leaves repository corrupted
- Git subprocess spawns but hangs indefinitely

**Mitigation Strategies**:

**Preventive Actions**:
1. **Comprehensive Error Handling**: Wrap all `Bun.spawn` calls with try-catch and validate exit codes
2. **Timeout Mechanisms**: Implement configurable timeouts (default 60s for clone, 30s for fetch)
3. **Authentication Validation**: Test SSH/HTTPS connectivity before operations
4. **Git Availability Check**: Validate Git installation and version at startup
5. **Retry Logic**: Exponential backoff for transient network failures (max 3 retries)

**Detective Controls**:
- Structured logging with Pino for all Git operations (url, duration, exit code, stderr)
- Metrics tracking for operation success/failure rates
- Error categorization (network, auth, permission, timeout)

**Corrective Actions**:
- Clear error messages guiding users to solutions
- Fallback to cached data when possible
- Manual retry capability through CLI

**Testing Requirements**:
1. **Unit Tests**:
   - Mock Git spawn with various exit codes (0, 128, 129)
   - Test timeout behavior with long-running mock processes
   - Verify retry logic with flaky network simulator
2. **Integration Tests**:
   - Test against real Git repositories (public and private)
   - Test all authentication methods (SSH keys, HTTPS tokens, no auth)
   - Test network failure scenarios (DNS failure, timeout, connection refused)
3. **Environment Tests**:
   - Test on macOS, Linux, and Windows (if supported)
   - Test with Git versions 2.30, 2.35, 2.40
   - Test with various shell environments (bash, zsh, fish)

**Residual Risk**: Medium - Even with comprehensive testing, edge cases in specific environments may remain

**Owner**: Development Team
**Timeline**: Must be complete before Story 3.7 PR merge

### 2. SEC-001: Malicious Template Repository Injection

**Score: 9 (Critical)**
**Category**: Security
**Probability**: High (3) - Attack vector is well-known and easily exploitable; users can provide arbitrary Git URLs
**Impact**: High (3) - Successful exploitation could lead to remote code execution, data exfiltration, or system compromise

**Affected Components**:
- `GitTemplateRepository` (clone/fetch operations)
- `TemplateLoader` (template file loading)
- Template execution during testing (TemplateTestRunner)

**Attack Scenarios**:

1. **Malicious Repository URL**:
   ```typescript
   // Attacker provides:
   repository: {
     type: 'git',
     url: 'file:///etc/passwd' // Local file access
   }
   ```

2. **Command Injection via Template**:
   ```yaml
   # template.yaml contains:
   - step: "Run cleanup"
     command: "rm -rf / # Dangerous command"
   ```

3. **Dependency Chain Poisoning**:
   - Attacker compromises popular template dependency
   - Malicious code executes during dependency resolution
   - Propagates to all dependent templates

4. **Manifest Exploit**:
   ```json
   {
     "name": "../../../malicious",
     "files": ["../../../sensitive-data.txt"]
   }
   ```

**Mitigation Strategies**:

**Preventive Actions**:
1. **URL Validation** (Critical):
   ```typescript
   // Implement strict whitelist validation
   function isValidRepositoryUrl(url: string): boolean {
     const allowedProtocols = ['https:', 'git:'];
     const parsed = new URL(url);

     // Block file:// protocol completely
     if (parsed.protocol === 'file:') {
       throw new SecurityError('file:// protocol not allowed');
     }

     // Require https:// or git@ only
     if (!allowedProtocols.includes(parsed.protocol)) {
       throw new SecurityError(`Protocol ${parsed.protocol} not allowed`);
     }

     return true;
   }
   ```

2. **Sandbox Execution** (Critical):
   - Use existing `TemplateSandbox` class from Story 3.1 for ALL template execution
   - Sandbox must restrict: file system access, network access, process spawning
   - Run templates with least privilege

3. **Dangerous Command Detection** (Critical):
   - Leverage existing `TemplateSecurity` class from Story 3.2
   - Scan templates for: `rm -rf`, `curl`, `wget`, `eval`, shell expansions
   - Block templates with dangerous patterns

4. **Manifest Validation** (Critical):
   - Strict Ajv schema validation (see story implementation details)
   - Reject path traversal patterns (`../`, absolute paths)
   - Validate all URLs (repository, homepage, bugs)
   - Limit string field lengths (name: 50, description: 200)

5. **Checksum Verification** (Critical):
   - Use `CryptoManager.createIntegrityHash()` from Story 3.2
   - Verify checksums for all downloaded templates
   - Store checksums in template index
   - Reject templates with mismatched checksums

6. **Audit Logging** (Critical):
   - Log ALL template operations: install, test, execute
   - Include: timestamp, user, template name/version, repository URL, outcome
   - Use existing audit logging infrastructure from Story 3.2

**Detective Controls**:
- Monitor for suspicious template activity (excessive file access, network calls)
- Alert on checksum mismatches
- Track template installation patterns

**Corrective Actions**:
- Quarantine mechanism for flagged templates
- Rollback capability for template installations
- Incident response procedures documented

**Testing Requirements**:
1. **Security Unit Tests**:
   - Test URL validation with file://, javascript:, data: protocols
   - Test path traversal in manifest names and file paths
   - Test command injection in template steps
   - Test checksum mismatch scenarios
2. **Penetration Testing**:
   - Attempt to bypass sandbox restrictions
   - Test malicious template scenarios from attack scenarios above
   - Fuzz manifest fields for injection vulnerabilities
3. **Integration Tests**:
   - End-to-end test with known-good and known-bad templates
   - Verify audit logs capture all operations
   - Test rollback procedures

**Residual Risk**: Low - With comprehensive security controls, risk is minimized but zero-day vulnerabilities may exist

**Owner**: Development Team + Security Review Required
**Timeline**: Must be complete and security-reviewed before Story 3.7 PR merge

## High-Priority Risks (Score 6)

### 3. TECH-002: Circular Dependency Detection Reliability

**Score: 6 (High)**
**Category**: Technical
**Probability**: Medium (2) - Depth-first search algorithm is complex with edge cases
**Impact**: High (3) - Undetected circular dependencies cause infinite loops, system hangs, or stack overflow

**Mitigation**:
- Implement robust DFS with `visiting` and `visited` sets (see story implementation)
- Add maximum depth limit of 10 levels
- Implement timeout protection (5s max for dependency resolution)
- Comprehensive unit tests for circular dependency scenarios:
  - Simple cycle: A → B → A
  - Complex cycle: A → B → C → D → B
  - Self-reference: A → A
  - Deep chain before cycle: A → B → C → ... → Z → A

**Testing Priority**: High - Must test all circular dependency patterns

---

### 4. SEC-002: Template Manifest Schema Injection

**Score: 6 (High)**
**Category**: Security
**Probability**: Medium (2) - Requires sophisticated attack on JSON schema validation
**Impact**: High (3) - Bypass security controls, inject malicious metadata

**Mitigation**:
- Strict Ajv JSON Schema validation (Draft-07)
- Schema enforces:
  - Name pattern: `^[a-z0-9-]+$` (kebab-case only)
  - Version pattern: semantic version regex
  - Description length: 10-200 characters
  - License: string validation (consider SPDX list validation)
  - Repository type: enum `['git']` only
  - URL format validation using Ajv `format: 'uri'`
- Reject any manifest with additional properties not in schema
- Sanitize all string fields before storage/display

**Testing Priority**: High - Fuzz testing recommended

---

### 5. SEC-003: Dependency Chain Attack

**Score: 6 (High)**
**Category**: Security
**Probability**: Medium (2) - Supply chain attacks are increasing in frequency
**Impact**: High (3) - Cascading compromise across dependent templates

**Mitigation**:
- Verify checksums for ALL dependencies (not just direct dependencies)
- Limit dependency depth to 10 levels maximum
- Warn users when dependency chains are deep (>5 levels)
- Implement optional dependency isolation (skip if unavailable)
- Consider: dependency pinning, lock files in future stories

**Testing Priority**: High - Test dependency chain scenarios

---

### 6. PERF-001: Large Repository Clone Times

**Score: 6 (High)**
**Category**: Performance
**Probability**: High (3) - Many Git repositories are large (>100MB)
**Impact**: Medium (2) - Degrades user experience, potential timeout failures

**Mitigation**:
- Use shallow clone `--depth=1` for all clone operations (already in story)
- Implement progress indicators for operations >5s
- Configurable timeout (default 60s, adjustable via config)
- Cache cloned repositories in `~/.bmad/cache/templates/`
- Clear error messages on timeout: "Clone timed out after 60s. Try: bmad config set clone-timeout 120"

**Performance Target**:
- Small repos (<10MB): <5s
- Medium repos (10-100MB): <30s
- Large repos (>100MB): <60s or fail with clear message

**Testing Priority**: Medium - Benchmark with various repository sizes
