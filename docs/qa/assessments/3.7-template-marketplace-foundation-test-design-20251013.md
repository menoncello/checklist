# Test Design: Story 3.7 - Template Marketplace Foundation

**Date**: 2025-10-13
**Designer**: Quinn (Test Architect)
**Story ID**: 3.7
**Story Title**: Template Marketplace Foundation

## Test Strategy Overview

- **Total test scenarios**: 58
- **Unit tests**: 35 (60%)
- **Integration tests**: 20 (35%)
- **E2E tests**: 3 (5%)
- **Priority distribution**: P0: 28, P1: 22, P2: 8, P3: 0

### Test Philosophy

This story implements critical infrastructure for template marketplace functionality with significant security and reliability risks. The test strategy emphasizes:

1. **Security-First Testing**: Comprehensive security validation for all template operations (SEC-001, SEC-002, SEC-003)
2. **Reliability Focus**: Extensive error handling tests for Git operations (TECH-001)
3. **Algorithm Verification**: Deep testing of dependency resolution logic (TECH-002)
4. **Performance Validation**: Benchmarks for critical operations (PERF-001)
5. **Shift-Left Approach**: 60% unit tests for fast feedback on complex logic

## Test Execution Strategy

### Phase 1: P0 Unit Tests (Fast Fail)

**Execute First** - These provide immediate feedback on core logic:

- Manifest validation (3.7-UNIT-001 to 017): ~2 minutes
- URL validation (3.7-UNIT-018 to 021): ~30 seconds
- Version constraint logic (3.7-UNIT-032 to 039): ~1 minute
- Dependency resolution algorithm (3.7-UNIT-041 to 049): ~2 minutes

**Total P0 Unit Time**: ~6 minutes
**Coverage**: 60% of critical logic validated

### Phase 2: P0 Integration Tests (Critical Paths)

**Execute Second** - Validate critical integrations:

- Git operations (3.7-INT-004 to 020): ~10 minutes (with mock repos)
- Manifest loading (3.7-INT-001 to 003): ~1 minute
- Dependency resolution integration (3.7-INT-034 to 036): ~3 minutes
- Version management (3.7-INT-029 to 031): ~2 minutes

**Total P0 Integration Time**: ~16 minutes
**Coverage**: Critical integration points validated

### Phase 3: P0 E2E Tests (End-to-End Validation)

**Execute Third** - Validate complete workflows:

- Complete repository workflow (3.7-E2E-001): ~5 minutes

**Total P0 E2E Time**: ~5 minutes
**Coverage**: Critical path validated end-to-end

### Phase 4: P1 Tests (Core Functionality)

**Execute Fourth** - Validate core features:

- Template discovery (3.7-UNIT-024 to 031, 3.7-INT-021 to 028): ~8 minutes
- Version sorting and comparison (3.7-UNIT-040, 3.7-INT-032 to 033): ~2 minutes
- Testing framework (3.7-UNIT-052 to 054, 3.7-INT-039 to 045, 3.7-E2E-002): ~10 minutes
- Example templates (3.7-INT-046 to 052, 3.7-E2E-003): ~8 minutes

**Total P1 Time**: ~28 minutes
**Coverage**: Core features validated

### Phase 5: P2 Tests (Documentation & Polish)

**Execute Last** - Manual documentation validation:

- Documentation completeness (3.7-MANUAL-01 to 08): Manual review

**Total P2 Time**: ~30 minutes (manual)
**Coverage**: Documentation quality assured

### Total Execution Time

- **Automated Tests**: ~57 minutes (P0: 27 min, P1: 30 min)
- **Manual Tests**: ~30 minutes
- **Overall**: ~1.5 hours for full test suite

### Unit Tests

- **Dependencies**: None (pure logic testing)
- **Mocks**: Bun.spawn (Git commands), Bun.file (file operations)
- **Tools**: Bun Test framework, Jest-style mocks

### Integration Tests

- **Dependencies**:
  - Git 2.30+ installed
  - Temporary test repositories (local file system)
  - Network access for remote index tests (can be mocked)

  - Mock Git repositories in `tests/fixtures/repositories/`

- **Tools**: Bun Test, temporary directory utilities

### E2E Tests

- **Dependencies**:
  - Full application build
  - CLI binary available
  - Git installed
  - Test repositories (can be local)
- **Environment**: Isolated test directory (~/.bmad-test/)
- **Tools**: Bun Test, CLI spawn utilities

## Test Maintenance Considerations

### High Maintenance Risk

- **Git integration tests** (3.7-INT-004 to 020): May break with Git version updates
  - Mitigation: Use Docker container with fixed Git version
  - Mitigation: Mock Bun.spawn for more stable tests

- **Example templates** (3.7-INT-046 to 052): Must be kept in sync with template format changes
  - Mitigation: Treat examples as first-class code with version control

### Low Maintenance Risk

- **Unit tests** (pure logic): Very stable, unlikely to break
- **Schema validation tests**: Stable, only change with schema updates

### Test Data Management

- Store test repositories in Git LFS if large
- Version test fixtures alongside code
- Document test data setup in `tests/fixtures/README.md`

## Security Testing Notes

### Penetration Testing Scenarios

Beyond automated tests, consider manual penetration testing:

1. **Template Injection**: Attempt to inject malicious code via manifest fields
2. **Path Traversal**: Try various path traversal patterns (../, ../../, etc.)
3. **Command Injection**: Attempt to inject shell commands in repository URLs
4. **DoS Attacks**: Test with extremely large manifests, deep dependency trees
5. **Credential Harvesting**: Verify tokens are never logged or exposed

### Security Review Checklist

- [ ] All URL validation tests pass (3.7-UNIT-018 to 021)
- [ ] Manifest injection tests pass (3.7-UNIT-001 to 017)
- [ ] Sandbox execution works correctly (3.7-INT-039)
- [ ] Credential sanitization tests pass (3.7-INT-017, 3.7-INT-018)
- [ ] External security review completed
- [ ] Dependency chain limits enforced (3.7-UNIT-047, 3.7-INT-036)
