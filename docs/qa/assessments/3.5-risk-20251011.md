## Critical Risks Requiring Immediate Attention

### 1. SEC-001: Template Injection via Unsafe Expression Evaluation

**Score: 9 (Critical)**
**Category:** Security
**Probability:** High (3) - Expression evaluation is inherently dangerous; even with AST parsing, vulnerabilities can exist
**Impact:** High (3) - Could lead to arbitrary code execution, data breach, system compromise

**Description:**
Despite using acorn for AST parsing, the evaluation of user-provided expressions in conditionals, math expressions, and functions creates multiple injection points. Attackers could craft malicious templates that bypass validation and execute arbitrary code.

**Affected Components:**
- `ConditionalEvaluator.ts` - Condition expression parsing
- `MathExpressionEvaluator.ts` - Math expression evaluation
- `TemplateFunctions.ts` - Function argument parsing
- `LoopEvaluator.ts` - Loop variable evaluation

**Attack Vectors:**
- Obfuscated expressions that pass AST validation but execute dangerous code
- Prototype pollution through `__proto__` access in nested contexts
- Function constructor smuggling via computed property access
- AST validation bypass through edge cases in acorn parsing

**Mitigation:**
1. **Implement Defense in Depth:**
   - Layer 1: Input validation with strict allowlists
   - Layer 2: AST validation blocking ALL dangerous node types
   - Layer 3: VM2 or isolated-vm for true sandboxing (consider replacing TemplateSandbox)
   - Layer 4: Runtime monitoring for suspicious patterns

2. **Specific Actions:**
   - Use allowlist approach for AST nodes (only permit safe operations)
   - Block ALL property access to dangerous objects (`__proto__`, `constructor`, `prototype`)
   - Implement expression complexity limits (max depth, max operations)
   - Add runtime value type checking before evaluation
   - Never pass full context objects - only whitelisted variables
   - Use frozen objects for all context variables
   - Implement CSP-style policies for template evaluation

3. **Testing Requirements:**
   - Security testing with OWASP attack patterns
   - Fuzzing with randomly generated malicious templates
   - Penetration testing of all expression types
   - Code review by security specialist
   - Automated security scanning in CI/CD

**Residual Risk:** Medium - Even with all mitigations, zero-day AST bypass vulnerabilities may exist
**Owner:** Dev Team + Security Review
**Timeline:** Must be resolved before Story 3.5 merge

### 2. SEC-002: Sandbox Escape Through AST Manipulation

**Score: 9 (Critical)**
**Category:** Security
**Probability:** High (3) - AST-based sandboxes have known bypass techniques
**Impact:** High (3) - Complete sandbox escape allows system-level access

**Description:**
The TemplateSandbox from Story 3.1 was designed for simpler use cases. Advanced features (nested structures, function calls, complex expressions) create new attack surfaces for sandbox escape.

**Affected Components:**
- `TemplateSandbox.ts` - Core sandbox implementation
- All evaluators that call `sandbox.evaluateSafely()`

**Known Bypass Techniques:**
- Indirect access to blocked globals via `this` or `globalThis`
- Constructor property access chains: `{}.constructor.constructor('code')()`
- Symbol-based property access bypassing string checks
- Error stack trace manipulation to access internal state
- Async function smuggling if promises not properly blocked

**Mitigation:**
1. **Sandbox Hardening:**
   - Review and update TemplateSandbox for advanced use cases
   - Block ALL constructor access paths (test extensively)
   - Freeze all prototype chains before evaluation
   - Use Proxy traps to intercept property access
   - Consider VM2 or isolated-vm for production use

2. **Specific Actions:**
   - Comprehensive security audit of TemplateSandbox
   - Add AST node type allowlist (only permit safe nodes)
   - Implement runtime object access monitoring
   - Add anomaly detection for unusual evaluation patterns
   - Create extensive sandbox escape test suite

3. **Testing Requirements:**
   - Attempt all known sandbox escape techniques
   - Fuzzing with malicious payloads
   - Third-party security audit
   - Continuous security regression testing

**Residual Risk:** Medium - New bypass techniques constantly discovered
**Owner:** Dev Team + External Security Auditor
**Timeline:** Must be resolved before Story 3.5 merge

### 3. PERF-001: Performance Requirement Breach (<50ms Target)

**Score: 9 (Critical)**
**Category:** Performance
**Probability:** High (3) - Complex templates with nesting easily exceed target
**Impact:** High (3) - Violates critical AC#8, unusable for real-world applications

**Description:**
The <50ms performance target for complex templates (AC#8) is extremely aggressive given the processing pipeline: variable substitution → math evaluation → function execution → conditionals → loops. Each evaluator adds latency, and nested structures compound the issue.

**Affected Components:**
- `TemplateEngine.ts` - Complete pipeline
- All evaluators (especially nested operations)
- AST parsing overhead in each evaluator

**Performance Bottlenecks:**
- Multiple regex passes over template string
- Repeated AST parsing for each expression
- No caching of parsed structures
- Nested evaluation recursion overhead
- String concatenation in loops (not using StringBuilder pattern)
- Variable resolution overhead in nested contexts

**Mitigation:**
1. **Implement Aggressive Optimization:**
   - Template compilation and AST caching (Task 7)
   - Single-pass template parsing (combine all patterns)
   - Lazy evaluation (don't process unused conditional branches)
   - String builder pattern for loop output
   - Variable context precomputation
   - JIT compilation for hot templates

2. **Specific Actions:**
   - Benchmark each evaluator in isolation
   - Profile complex template scenarios to identify hot paths
   - Implement template compilation cache with LRU eviction
   - Use Bun's native performance optimizations
   - Consider parallel evaluation for independent expressions
   - Add performance budgets per evaluator (e.g., conditionals <10ms)

3. **Testing Requirements:**
   - Comprehensive benchmarking suite with Tinybench
   - Performance regression tests in CI/CD
   - Real-world template complexity testing
   - Load testing with concurrent template evaluations
   - Memory profiling for cache efficiency

**Residual Risk:** Low if optimizations implemented; High if not addressed
**Owner:** Dev Team
**Timeline:** Must meet <50ms target before Story 3.5 acceptance

## High Risk Issues

### 4. SEC-003: Resource Exhaustion Through Malicious Templates

**Score: 6 (High)**
**Category:** Security
**Probability:** Medium (2) - Limits exist but may be insufficient
**Impact:** High (3) - DoS attack, system unavailability

**Description:**
Malicious templates could exhaust resources through:
- Deep nesting (10 levels allowed - stack overflow risk)
- Large loops (10,000 iterations - CPU/memory exhaustion)
- Complex expressions (no complexity limit defined)
- Recursive template references

**Mitigation:**
- Implement conservative resource limits (reduce max nesting to 5, max iterations to 1000)
- Add expression complexity scoring (max AST nodes)
- ResourceLimiter enforcement (CPU time, memory allocation)
- Circuit breaker for repeated failures
- Rate limiting for template evaluation requests

**Testing:** Chaos engineering with malicious templates, load testing

### 5. TECH-001: Integration Complexity Between Evaluators

**Score: 6 (High)**
**Category:** Technical
**Probability:** High (3) - 5-stage pipeline with interdependencies
**Impact:** Medium (2) - Bugs, incorrect output, maintenance difficulty

**Description:**
The pipeline design (Variable substitution → Math → Functions → Conditionals → Loops) creates tight coupling and order dependencies. Changes to one evaluator could break others.

**Mitigation:**
- Comprehensive integration tests for all permutations
- Contract testing between evaluators
- Immutable context passing (no shared state mutations)
- Clear interface definitions with validation
- Extensive documentation of pipeline order rationale

**Testing:** Integration test suite covering all feature combinations

---

### 6. DATA-001: Variable Context Corruption in Nested Structures

**Score: 6 (High)**
**Category:** Data Integrity
**Probability:** Medium (2) - Nested contexts are complex
**Impact:** High (3) - Wrong data in output, silent failures

**Description:**
Loop contexts with special variables (`@index`, `@first`, `@last`) and nested loop parent references could lead to variable shadowing, incorrect scoping, or context corruption.

**Mitigation:**
- Immutable context objects (freeze after creation)
- Explicit variable scoping rules with validation
- Context debugging tools (log full context at each level)
- Extensive test coverage for deeply nested scenarios
- Static analysis to detect potential shadowing

**Testing:** Nested structure tests (Task 9 - AC#4)

---

### 7. PERF-002: Memory Leaks from Template Caching

**Score: 6 (High)**
**Category:** Performance
**Probability:** Medium (2) - Caching without proper eviction
**Impact:** High (3) - Memory exhaustion over time

**Description:**
Task 7 requires template compilation caching, but no cache eviction strategy is specified. Unbounded cache growth could lead to memory leaks.

**Mitigation:**
- Implement LRU cache with configurable max size
- Memory monitoring and alerts
- Cache statistics (hit rate, size, evictions)
- Automatic cache clearing on memory pressure
- Consider WeakMap for template caching

**Testing:** Memory profiling, long-running stress tests

### 9. TECH-002: Regex Performance Issues with Large Templates

**Score: 4 (Medium)**
**Probability:** Medium (2) - Regex patterns used extensively
**Impact:** Medium (2) - Catastrophic backtracking, slow processing

**Description:**
Multiple regex patterns (conditionals, loops, functions, math) with greedy quantifiers could cause catastrophic backtracking on malicious input.

**Mitigation:**
- Use non-backtracking regex where possible
- Add input size limits
- Timeout enforcement for regex operations
- Consider switching to manual parsing for complex patterns
- ReDoS testing with pathological inputs

**Testing:** Performance testing with large templates, ReDoS fuzzing

---

### 10. TECH-003: Insufficient Error Context in Nested Evaluation

**Score: 4 (Medium)**
**Probability:** Medium (2) - Deep nesting makes debugging hard
**Impact:** Medium (2) - Poor developer experience, hard to fix bugs

**Description:**
Error messages from deeply nested evaluations may not provide sufficient context (which level, which expression, current variable state).

**Mitigation:**
- Structured error objects with full context (file, line, expression, variables)
- Error context accumulation through evaluation stack
- Source mapping for compiled templates
- Debug mode with verbose logging
- User-friendly error messages with suggestions

**Testing:** Error scenario testing, developer usability testing

## Appendix: Risk Assessment Methodology

**Probability Scoring:**
- **High (3):** >70% chance based on complexity, known issues, past experience
- **Medium (2):** 30-70% chance based on moderate complexity, some unknowns
- **Low (1):** <30% chance based on simple implementation, well-understood patterns

**Impact Scoring:**
- **High (3):** Security breach, system unavailability, data loss, critical AC failure
- **Medium (2):** Performance degradation, minor data issues, user inconvenience
- **Low (1):** Cosmetic issues, documentation gaps, minor technical debt

**Risk Score = Probability × Impact:**
- **9 (Critical):** Immediate attention required, blocks progress
- **6 (High):** Must be addressed before deployment
- **4 (Medium):** Should be addressed, can deploy with mitigation
- **2-3 (Low):** Accept with documentation and monitoring
- **1 (Minimal):** Accept as-is
